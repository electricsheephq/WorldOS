# Sparkle auto-update setup for WorldOS

Sparkle (https://sparkle-project.org) is the de-facto macOS auto-update framework. It pairs cleanly with the **Developer ID signing** that `script/build_and_run.sh` already prefers (commit 78645a3) and ends the "popup every rebuild" pattern for good: every published release inherits the same Developer ID identity, so users approve once and never see another security re-evaluation.

This guide is the step-by-step to enable Sparkle on the existing WorldOS app. It is intentionally **not** wired in `Package.swift` yet — bundled XPC services require careful signing/notarization, and the first build with Sparkle live should be a deliberate one-off. Everything below is a one-time setup.

---

You already have these (verified 2026-05-28):

- A **Developer ID Application** identity in your login keychain (`security find-identity -v -p codesigning` shows `Andrew Ryan (TC6MS3T6NN)`).
- The build script auto-uses it when the keychain ACL allows. After one Keychain "Always Allow" click, every rebuild signs silently.

You will need (one-time):

- An **EdDSA key pair** for signing release updates (Sparkle's own format, separate from your Developer ID).
- A **public hosting target** for the appcast XML feed — GitHub Releases is the no-cost path.

## Step 1 — Add Sparkle to Swift Package Manager

`macos/WorldOSApp/Package.swift`:

```swift
// swift-tools-version: 5.9

import PackageDescription

let package = Package(
    name: "WorldOSApp",
    platforms: [.macOS(.v13)],
    products: [.executable(name: "WorldOSApp", targets: ["WorldOSApp"])],
    dependencies: [
        // Sparkle 2.x — modern, SPM-friendly, XPC-isolated auto-updater.
        .package(url: "https://github.com/sparkle-project/Sparkle.git", from: "2.6.0"),
    ],
    targets: [
        .executableTarget(
            name: "WorldOSApp",
            dependencies: [.product(name: "Sparkle", package: "Sparkle")]
        ),
    ]
)
```

The first `swift build` after this change downloads Sparkle and its XPC services.

---

## Step 2 — Add an Updater wrapper

Create `macos/WorldOSApp/Sources/WorldOSApp/Services/SparkleUpdater.swift`:

```swift
import Foundation
import Sparkle

/// Thin SwiftUI-friendly wrapper around Sparkle's standard updater controller.
/// Reads SUFeedURL + SUPublicEDKey from Info.plist; if the public key is absent
/// (development / pre-release builds), the updater logs and stays passive so we
/// don't crash an unsigned build.
final class SparkleUpdater: ObservableObject {
    let controller: SPUStandardUpdaterController

    init() {
        // startingUpdater: true   — checks for updates on launch (per SUEnableAutomaticChecks).
        // updaterDelegate: nil    — keep the SwiftUI scaffold light; add a delegate later.
        // userDriverDelegate: nil — default UI is fine.
        controller = SPUStandardUpdaterController(
            startingUpdater: true,
            updaterDelegate: nil,
            userDriverDelegate: nil
        )
    }

    @objc func checkForUpdates(_ sender: Any?) {
        controller.checkForUpdates(sender)
    }
}
```

---

## Step 3 — Wire it into the app + menu

`WorldOSApp.swift` — add a `@StateObject` and a menu item:

```swift
@main
struct WorldOSApp: App {
    @StateObject private var updater = SparkleUpdater()
    // ...existing @StateObject properties

    var body: some Scene {
        WindowGroup {
            RootView()
                // ...existing modifiers
        }
        .commands {
            CommandGroup(after: .appInfo) {
                Button("Check for Updates…") {
                    updater.checkForUpdates(nil)
                }
            }
            // ...existing commands
        }
    }
}
```

---

## Step 4 — Info.plist entries

`script/build_and_run.sh` writes the Info.plist inline. Add two keys to the plist heredoc (inside the existing `<dict>`):

```xml
<key>SUFeedURL</key>
<string>https://github.com/electricsheephq/WorldOS/releases/latest/download/appcast.xml</string>
<key>SUPublicEDKey</key>
<string><!-- Paste the public key generated by Sparkle's generate_keys tool here --></string>
<key>SUEnableAutomaticChecks</key>
<true/>
```

---

## Step 5 — Generate the EdDSA key pair (one-time)

Sparkle ships a `generate_keys` tool inside its package. After Step 1's first build:

```bash
.build/checkouts/Sparkle/bin/generate_keys
```

This stores the **private key** in your keychain (item name "https://sparkle-project.org") and prints the **public key** to stdout. Paste the public key into Info.plist (Step 4). Keep the keychain item private — anyone with it can sign updates that your users will accept.

---

## Step 6 — Build the appcast.xml

After every release tag, build an appcast entry. Sparkle ships a `generate_appcast` tool that takes a folder of `.zip` (or `.dmg`) update bundles and produces an `appcast.xml`:

```bash
# Stage signed-and-notarized .zip of the new app build at ./updates/
.build/checkouts/Sparkle/bin/generate_appcast updates/
# Result: updates/appcast.xml
```

Upload `appcast.xml` to the corresponding GitHub Release (matching the SUFeedURL in Info.plist).

---

## Step 7 — Notarization (the only remaining piece)

For Sparkle to verify and install an update, the new `.zip` must be **notarized** by Apple. This is the same notarization that's currently "deferred to 1.0.1" in the project plan — Sparkle is a natural prompt to finish it.

```bash
xcrun notarytool submit WorldOS-1.0.2.zip --apple-id <you@example.com> --team-id TC6MS3T6NN --wait
xcrun stapler staple WorldOS-1.0.2.zip
```

---

## What this gives you

- **Persistent permissions across rebuilds.** A Developer ID-signed and notarized app has a stable code signature, so macOS TCC grants + NordVPN-style file scanners cache their verdict per identity. No more popup every rebuild.
- **Real auto-update flow.** Users get "Check for Updates…" in the menu and an automatic check on launch.
- **No hosted backend.** GitHub Releases hosts the appcast + the signed `.zip` for free.

## What this does NOT give you

- A way around the **first-ever** TCC / security-scanner prompt on the very first install of a brand-new identity. That's still one click — but only one, ever.
- An auto-update path for **plugin** distribution. WorldOS ships as both a desktop app and a Claude Code plugin; Sparkle handles the app side only.
