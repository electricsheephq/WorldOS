## Research digests (full, per angle)

### Engines & shipped-game techniques
Shipped isometric RPGs (PoE1/2, Tyranny, Torment: ToN) share one Obsidian-originated pipeline: Maya renders each background scene as 4 baked passes (final/albedo, depth, normal) via Mental Ray, imported into Unity where an orthographic camera is placed to match the render's perspective; 3D characters composite on top using the depth pass for per-pixel occlusion, the normal pass + a 2-directional-light rig (key+fill) for lighting, and background-color-sampling for pseudo-GI. Disco Elysium (ZA/UM) used a parallel hand-painted-oil variant of the same depth/lighting compositing, covered in a dedicated GDC Summer 2020 talk. No off-the-shelf Unity asset fully replicates this AAA pipeline, but a $12.99 Built-in-RP-compatible asset (Retro PreRendered Backgrounds System) and a free MIT GitHub framework (ImposterSyndrome_PrerenderedSystem) cover the core depth-occlusion shader technique; Adventure Creator ($80) bundles a mature 2.5D pre-rendered-background camera+masking subsystem inside a full adventure-game framework. No clearly documented shipped Unity title yet combines AI-diffusion-painted backdrops with real-time 3D characters — that pairing (which is WorldOS's approach) is not a proven, copyable indie pattern yet.

**Findings:**
- PoE background pipeline: Maya renders 4 passes per scene — final(albedo), depth, normal — combined in Unity for per-pixel occlusion + dynamic lighting. Source: Obsidian dev update #79 by lead programmer Adam Brennecke, https://eternity.obsidian.net/eternity/news/update--79-graphics-and-rendering-
- Character lighting rig: 2 directional lights (key=sun/moon color+intensity tied to day/night cycle, fill=prevents pitch-black backside) plus dynamic deferred lights (torches, spell FX) that hit both the 2D bg and 3D chars. Source: same PoE update #79.
- Grounding/GI hack: an 'ambient system' samples color from the 2D background pixel under each character to fake GI (e.g. green tint in jungle); a separate shadow system samples a low-res greyscale map of the background to darken characters walking into painted shadow, color-matched to the 2D shadow's blue hue. Source: PoE update #79.
- Fan technical analysis: this is effectively a pre-baked deferred renderer — depth/normal/albedo G-buffer computed offline in Maya instead of at runtime — trading full runtime GI/dynamic shadows for near-zero runtime compositing cost + huge texture footprint (multi-GB source renders, per-pass compression tradeoffs). Source: https://projectionspace.wordpress.com/2016/05/06/pillars-of-eternitys-rendering-techniques/
- Same tech was licensed/shared across studios: PoE tech (Unity 4.5→5) was reused for Tyranny and licensed to inXile for Torment: Tides of Numenera; T:ToN scenes modeled in 3ds Max, lit/rendered in Maya+Mental Ray, then imported as flat images with 3D characters/props composited on top in Unity. Source: Polycount artist post-mortem https://polycount.com/discussion/185595/tyranny-torment-tides-of-numenera-mini-dump and ArtStation notes.
- Disco Elysium (ZA/UM) has a dedicated primary-source GDC talk: 'Turpentine Fumes and Shaders: Art Tech in Disco Elysium' by technical artist Siim Raidma (GDC Visual Arts track, originally GDC2020/rescheduled to GDC Summer 2020) — covers producing hand-painted, dynamically-lit backgrounds for an isometric RPG from scratch over 4 years. Source: https://www.gamedeveloper.com/art/come-to-gdc-and-see-how-i-disco-elysium-i-s-unique-style-was-achieved-
- Practical Unity depth-testing shader for pre-rendered isometric bg (community-derived, matches PoE approach): encode world XYZ into separate baked textures per background, in a fragment shader reconstruct depth via `float4 vertex_p = float4(x,z,y,1); mul(UNITY_MATRIX_MVP, vertex_p)` and output to SV_DEPTH so 3D characters are correctly occluded by painted geometry. Source: https://discussions.unity.com/threads/pre-rendered-background-with-depth-testing-isometric.335010/
- Simpler 'depth mask' occlusion shader for an invisible volume: SubShader tag Queue=AlphaTest(~2001, just after Geometry@2000), Lighting Off, ZTest LEqual, ZWrite On, ColorMask 0, empty color pass — writes to depth buffer only, carving an invisible occlusion volume that hides a 3D character behind painted foreground elements without rendering any color. Source: https://discussions.unity.com/t/depth-mask-occlusion-shader/805569
- NavMesh authoring for pre-rendered isometric scenes: standard community pattern is an invisible 3D plane/proxy geometry placed to match the implied 3D volume of the painted background, NavMesh baked on that proxy; camera must be placed at the actual angled (dimetric/isometric) perspective used in the source render — a straight top-down camera makes characters read as flat top-down sprites instead of matching the painted perspective. Source: https://discussions.unity.com/threads/2-5d-isometric-navmesh-pillars-of-eternity-like/213458
- Adventure Creator (Unity Asset Store, ICEBOX Studios, $80+VAT, Unity Personal/Plus/Pro 2017.4+) ships a built-in '2.5D' mode: 3D characters + NavMesh moving through a proxy volume matched to a static background image, a dedicated 2.5D Camera (Perspective projection, FOV matched to the source photo/render) and a background-mask sprite that occludes 3D objects; ships with URP add-on script but core is Built-in-RP native. Shipped games: Harold Halibut, Sally Face, Little Misfortune. Source: https://assetstore.unity.com/packages/tools/game-toolkits/adventure-creator-11896 and https://adventurecreator.org/tutorials/making-25d-game
- PowerQuest (Powerhoof) is a free Unity point-and-click framework (not asset-store, itch.io/powerquest.powerhoof.com) aimed at 2D sprite-based adventures, positioned as simpler/lighter than Adventure Creator; not itself a pre-rendered-background/3D-character isometric solution (2D-only, no 2.5D depth compositing). Source: https://powerquest.powerhoof.com/
- Free MIT-licensed GitHub framework 'ImposterSyndrome_PrerenderedSystem' directly implements the PoE-style stack: an 'IsometricOrtho' system (Baldur's Gate/Infinity Engine-style orthographic pre-rendered bg + click-to-move + pan/zoom) plus depth-compositing shaders credited to Florian Mehm (SpookyFM); backgrounds authored in Maya; explicitly notes AA must be disabled in Quality settings for the depth trick to work; WIP/unmaintained but usable as reference code. Source: https://github.com/ImposterSyndromeGames/ImposterSyndrome_PrerenderedSystem
- Commercial narrow-scope asset 'Retro PreRendered Backgrounds System' (RetroGig, $12.99, Unity 6000.0.46f1+, v1.2 May 2025) is explicitly Built-in RP AND URP compatible (not HDRP) and provides depth occlusion + shadow-casting between real-time 3D elements and pre-rendered/externally-rendered background images — closest direct off-the-shelf match to the PoE technique for a Built-in-pipeline project. Source: https://assetstore.unity.com/packages/vfx/shaders/fullscreen-camera-effects/retro-prerendered-backgrounds-system-309901
- HD-2D (Octopath Traveler-style pixel-art-over-3D-environment) is a real, named technique but was built by Acquire in Unreal Engine 4, not Unity; no equivalent turnkey Unity asset-store 'HD-2D kit' exists — only scattered itch.io pixel-art packs that must be self-composited with 3D. Source: https://www.unrealengine.com/en-US/spotlights/octopath-traveler-s-hd-2d-art-style-and-story-make-for-a-jrpg-dream-come-true
- Modern indie 'pre-rendered background' games (Crow Country 2024) mostly FAKE the look with real-time 3D + camera filters/fixed angles rather than true pre-rendered/depth-composited images — Crow Country's own dev says the pre-rendered aesthetic 'happened by accident' from detailed real-time textures + CRT filter, built in Unity with Playmaker+ProBuilder, not a depth-compositing pipeline. Source: https://www.pushsquare.com/games/ps5/crow_country and ResetEra thread.
- No verified shipped Unity title combining AI-diffusion-painted 2D backdrops with real-time 3D characters was found in this research; current AI-in-Unity devlogs (e.g. BigDevSoon's 10-day roguelite using Recraft V4 Pro for backgrounds + Claude Code) are 2D-only or prototype-stage, and 2026 testing reports note AI art gets you '~80% of an asset in 60s, last 20% still by hand' — treat the AI-backdrop+3D-char pairing as unproven territory, not a pattern to copy. Source: https://bigdevsoon.me/blog/building-games-with-ai-indie-game-dev-workflow/ and https://www.3daistudio.com/blog/best-ai-game-asset-generators-2026
- Animated water/overlay layers on 2D backdrops: standard technique is a transparent overlay shader rendered after the opaque queue (`Blend SrcAlpha OneMinusSrcAlpha, ZWrite Off`) using a scrolling distortion+noise texture for ripple/shoreline animation — directly portable to a painted-backdrop quad as an extra transparent layer. Source: https://roystan.net/articles/toon-water/ and https://lindenreidblog.com/2018/01/31/2d-reflective-water-shader-in-unity/

**Actionable:**
- Bake a depth pass alongside each AI-painted backdrop (even a coarse hand-authored depth/height map is enough) and use it to write SV_DEPTH via the community shader pattern, so 3D actors get correct per-pixel occlusion behind painted foreground props — this is the single highest-leverage missing piece vs PoE's approach.
- Add a cheap 'depth-mask' invisible-volume shader (ZWrite On, ColorMask 0, Queue~2001) for hand-placed occlusion volumes (pillars, walls) where a full depth-map bake is overkill — fast to author per-scene.
- Adopt the 2-directional-light (key+fill) rig plus a background-color-sampling ambient hack to ground 3D actors into painted backdrops without full runtime GI — matches WorldOS's orthographic dimetric camera setup closely.
- Bake NavMesh on an invisible proxy plane/geometry matched to the backdrop's implied 3D volume, and verify the dimetric camera angle matches the volume's authored perspective (not a straight top-down look) so characters read correctly against the art.
- Evaluate the $12.99 'Retro PreRendered Backgrounds System' (assetstore id 309901, Built-in RP compatible) as a fast reference/starting shader instead of writing the depth-occlusion shader from scratch.
- Pull reference code from the free MIT 'ImposterSyndrome_PrerenderedSystem' GitHub repo's IsometricOrtho system + SpookyFM depth-compositing shader rather than reinventing it.
- Add a transparent scrolling-noise overlay shader (Roystan toon-water pattern) as the generic mechanism for animated water/fog/mist overlays on the camera-locked backdrop quad.
- Do not adopt Adventure Creator/PowerQuest wholesale (they bundle dialogue/inventory/point-and-click frameworks irrelevant to a D&D engine) — if evaluated at all, scope it to just inspecting their 2.5D camera + background-mask subsystem for ideas, not as a dependency.

**Dead ends:**
- Chasing an 'HD-2D kit' for Unity: the Octopath Traveler HD-2D technique is Unreal-native (Acquire, UE4); no turnkey Unity Built-in-RP equivalent exists on the Asset Store.
- Using Crow Country as a technical reference: despite its 'pre-rendered background' reputation, it's real-time 3D + camera filter, not depth-composited pre-rendered art — no transferable occlusion/depth technique there.
- Looking for a proven 'AI-painted backdrop + 3D character' shipped indie precedent: none was found; current AI-art devlogs are 2D-only or prototype-stage, so don't treat this as a de-risked, copyable pattern.
- Adopting the full AAA offline-render pipeline (Maya + Mental Ray, dedicated lighting artist, multi-GB per-scene passes) as-is — it's sized for a studio pipeline with a rendering specialist; the transferable core for WorldOS is just the depth-mask/occlusion + 2-light-rig technique, not the whole offline pass pipeline.
- Buying Adventure Creator ($80) as infrastructure: it's an opinionated full adventure-game framework (inventory, dialogue trees, point-and-click state machine) that would fight WorldOS's own D&D engine rather than slot in cleanly.

### AI depth/segmentation from paintings
Depth-from-single-painted-image and segmentation are both mature as open components (SAM2, DepthAnythingV2, Marigold, ZoeDepth), but no shipped precedent does WorldOS's exact move (painted plate -> AI depth/seg -> Unity occlusion+walkmask). Every AA/AAA isometric precedent (PoE, Tyranny, Disco Elysium, Kingmaker) instead bakes depth as a rendered pass from the SAME 3D scene the painting comes from -- they never infer depth post-hoc from a finished painting. WorldOS has no 3D source, so this is a real gap to fill, not a recipe to copy. Stylized/abstract art is a documented depth-model weak spot (flat-plane misreads); Apache-2.0/MIT models exist (DepthAnythingV2-Small, Marigold, ZoeDepth, SAM2) but larger/higher-quality variants are often CC-BY-NC or bespoke-licensed. Best assembly: bake-time SAM2 prop segmentation feeding Unity's built-in alpha-outline collider generator for drift-free walkmasks, plus a depth pass (validated per-art-style, likely needing manual paint-over touch-up) for occlusion ordering.

**Findings:**
- SOTA depth models (incl. successors built on DepthAnythingV2 principles) still misread highly abstract/painterly styles (ink wash) as flat planes per DepthMaster paper -- arxiv.org/pdf/2606.12368, emergentmind.com/topics/depth-anything-v2
- Depth Anything V2 license split: Small=Apache-2.0 (commercial OK); Base/Large/Giant=CC-BY-NC-4.0 (non-commercial only) -- github.com/DepthAnything/Depth-Anything-V2 issues #162, #320
- Marigold (SD2-backbone diffusion depth) is Apache-2.0 since Dec-2023, strong on non-photo domains via synthetic training + generative prior, but multi-step diffusion = slow/bake-time only -- github.com/prs-eth/Marigold
- ZoeDepth (isl-org) is MIT-licensed and gives absolute METRIC depth, not just relative -- github.com/isl-org/ZoeDepth
- SAM2 code/weights are Apache-2.0 (commercial OK); SA-1B/SA-V training datasets are CC-BY-4.0/research-only but that doesn't restrict use of the released model -- github.com/facebookresearch/sam2/blob/main/LICENSE
- SAM2 zero-shot generalizes to unseen categories/styles via point/box/mask prompts, well suited to stylized hand-painted props not in any training taxonomy -- ai.meta.com/sam2
- Every shipped precedent found (Pillars of Eternity, Tyranny, Torment, Disco Elysium, Pathfinder Kingmaker) bakes occlusion depth by rendering the SAME 3D scene the background derives from (Maya final/depth/normal/albedo passes) -- eternity.obsidian.net/eternity/news/update--79-graphics-and-rendering-, projectionspace.wordpress.com/2016/05/06/pillars-of-eternitys-rendering-techniques, gamebanshee.com/news/121823-disco-elysium-from-render-to-paintover.html
- No prior art found of a team deriving real-time occlusion from a purely hand-painted background via post-hoc monocular AI depth (no 3D source) -- appears to be a genuine unfilled niche, confirmed by absence across multiple targeted searches
- Baldur's Gate 3's acclaimed 'walk behind walls' effect is NOT a depth map -- it's a dynamic runtime spherecast (char-to-camera) driving a shader cutout sphere mask, a different problem (near-camera occluder visibility) -- 80.lv/articles/artist-recreated-baldur-s-gate-3-occlusion-cutout-effect, artstation.com/artwork/WXVnyD
- Original Infinity Engine (BG1/2) used hand-authored 2D wall polygons dithering sprites for 'walk behind' plus separate SR.BMP/HT.BMP search+height maps for walkability/elevation -- fully authored, pre-AI technique -- gibberlings3.github.io/iesdp WED file format docs
- Unity has a built-in alpha-cutout-to-collider path: Sprite Editor 'Custom Physics Shape' auto-traces the opaque region into a tunable polygon outline -- exactly the drift-free walkmask mechanism WorldOS wants IF a prop is first isolated as its own cutout -- docs.unity3d.com/6000.3/Documentation/Manual/sprite/create-collision-geometry.html
- Third-party Unity tools (2D ColliderGen, open-source MeshCreator) do the same alpha-to-collider conversion in batch, outputting MeshCollider or PolygonCollider2D -- forum.unity.com '[RELEASED] 2D ColliderGen', github.com/uclagamelab/MeshCreator
- SPRITETOMESH (2026 arxiv paper) auto-converts a single sprite to an animation mesh via U-Net/EfficientNet-B0 segmentation (100k+ sprite-mask pairs, IoU 0.87) plus classical contour/Delaunay steps, 300-1200x faster than manual -- direct precedent for learned-seg + classical-geometry hybrids, though targets 2D skeletal mesh not depth/collision -- arxiv.org/abs/2602.21153
- DepthAnythingV2-Small is fast enough for real-time-class use (reported ~40-70fps GPU, though real ONNX/production throughput is often much lower) while Marigold (diffusion) and full SAM2 (large ViT, ~24x-1145x slower than lightweight detectors per one comparison) are realistically bake-time/offline tools only -- github.com/DepthAnything/Depth-Anything-V2, docs.ultralytics.com/models/sam-2
- PixelLab's 'Image to Image (depth)' tool (already in WorldOS's asset-gen toolchain) is depth-CONDITIONED generation (ControlNet-depth-style, makes new art match a reference's structure), NOT depth extraction from a finished painting -- do not mistake it for a depth-map exporter -- pixellab.ai/docs/tools/image-to-image-depth

**Actionable:**
- Treat this as bake-time, not runtime: run SAM2 + a depth model once per finished plate offline, ship the derived masks/depth texture as a build asset -- do not do live ML inference in the Unity player.
- License-gate model choice: use DepthAnythingV2-SMALL specifically (Apache-2.0); Base/Large/Giant are CC-BY-NC-4.0 and would block commercial WorldOS use. ZoeDepth (MIT) is a safe metric-depth alternative.
- Validate depth quality against 3-5 REAL WorldOS painterly plates before committing to a pipeline -- abstract/painterly styles are a documented failure mode (flat-plane misreads) across DepthAnything/DepthMaster/UniK3D-class models.
- For walkmasks specifically: don't ask a depth model to produce collision. Use SAM2 to carve each prop into its own alpha cutout, then feed that cutout through Unity's native Sprite Editor 'Custom Physics Shape' (or open-source MeshCreator/2D ColliderGen) to auto-trace a polygon collider -- zero drift because it traces the actual painted pixels.
- For the depth-quad/occlusion trick: since WorldOS plates have no underlying 3D source (unlike PoE/Disco Elysium's render-then-paint-over pipeline), expect the AI depth pass to need manual touch-up per plate rather than being a one-shot automatic solution.
- Consider Marigold over feed-forward depth nets specifically for painted plates given its generative SD prior and Apache-2.0 license, but budget for slow multi-step diffusion inference (offline-only, not iteration-speed).
- Do not adopt Apple Depth Pro without reviewing its bespoke license text line-by-line -- it is not a standard MIT/Apache license and carries higher legal-review overhead than DepthAnythingV2-Small/ZoeDepth/Marigold.
- Budget engineering time to BUILD the painted-plate depth+walkmask pipeline in-house -- no open pipeline or asset-store product does this exact composition today; component parts exist but the glue is unbuilt.

**Dead ends:**
- Don't chase BG3's spherecast/shader-cutout 'walk behind walls' trick -- it solves near-camera occluder visibility around the player, not per-pixel occlusion ordering of actors against arbitrary painted props.
- Don't use PixelLab's 'Image to Image (depth)' tool expecting a depth-map exporter -- it conditions NEW generation on a reference's structure, the reverse of extraction.
- Don't rely on Depth-Anything-V2 Base/Large/Giant (or any CC-BY-NC-licensed model) if WorldOS art ships commercially -- license blocks it outright regardless of quality gains.
- Don't expect real-time in-player depth inference on full-res painterly plates -- SAM2-full and Marigold are both far too slow for per-frame runtime use; this is strictly a bake-time asset step.
- Don't assume generic 'depth map to Unity mesh' parallax/HDRP-displacement tutorials transfer directly -- they're tuned for photographic height maps and 3D-photo parallax, not for validating occlusion correctness against arbitrary painted prop silhouettes.

### Animated living-scene layers
Making a still painted backdrop feel alive is a solved problem across three eras of tooling: classic real-time shader tricks (flow maps, normal-mapped lighting, vertex-anim wind, flipbook particles), AI image-to-video loop generation for baking elemental motion offline, and the proven isometric-RPG playbook (Pillars of Eternity / Deadfire, Disco Elysium) of layering a FEW real-time animated elements (water plane, particles, wildlife, torches) on top of an otherwise-static painted plate rather than animating the painting itself. For Unity built-in RP + Metal on macOS, the load-bearing constraint is that URP-only features (Sprite-Lit-Default+Light2D, Shader Graph, geometry-shader tricks) do not exist on built-in RP — normal-mapped 2D lighting and flipbook UV animation must be hand-rolled in CG/HLSL ShaderLab, and Metal has real gaps (no geometry shaders, historical MSAA bugs) worth testing early.

**Findings:**
- Flow-map shaders (two normal/flow textures, phase-blended UV distortion) originated at Valve's SIGGRAPH 2010 talk and were detailed for Portal 2 nonstandard textures at GDC 2011; Catlike Coding's Unity tutorial implements the exact phase-blend/jump-offset math usable for a backdrop water or lava region. https://catlikecoding.com/unity/tutorials/flow/texture-distortion/ ; https://unity.com/blog/engine-platform/new-hdrp-water-system-in-2022-lts-and-2023-1
- Disco Elysium (ZA/UM, GDC 2020 'Turpentine Fumes and Shaders' by Siim Raidma): the sea was a flat 3D plane with a custom shader over the painted heightmap-rendered background, using a flow map to fake directional water flow, a warm color-gradient overlay for shallow/deep read, and hand-painted TRANSPARENT plants each on its own distortion-shaded plane (camera angle was fixed so painted-on-transparency worked); the same shader drove ripples, fish swarms, wobbling icebergs, and seagulls. https://discoelysium.com/devblog/2019/01/23/from-render-to-paintover ; https://www.gamedeveloper.com/art/come-to-gdc-and-see-how-i-disco-elysium-i-s-unique-style-was-achieved-
- Disco Elysium's rule of thumb: paint only what's permanently static; EVERYTHING animated, pickup-able, or time-gated (NPCs, vegetation, collectibles, particles) is a separate real-time layer composited over the painted plate, not baked into the painting. https://www.gamedeveloper.com/art/come-to-gdc-and-see-how-i-disco-elysium-i-s-unique-style-was-achieved-
- Pillars of Eternity / Deadfire (Obsidian): backgrounds are pre-rendered STATIC Maya output in 4 passes (final/depth/normal/albedo) composited in Unity for per-pixel 3D-object occlusion and dynamic lighting; water is a separate 3D mesh/plane VFX converts and animates over the plate; an 'ambient system' samples background color to ground 3D characters (quick dirty GI), and deferred lights (torches, fireball bursts) illuminate both the 2D plate and 3D characters together. https://eternity.obsidian.net/eternity/news/update--79-graphics-and-rendering- ; https://eternity.obsidian.net/eternity/news/pillars-of-eternity-ii-deadfire-update-30---from-blockout-to-completion-the-environments-of-pillars-ii
- Pillars of Eternity's pre-baked-pass pipeline sacrifices real dynamism: 'traditional shadow mapping isn't going to work... dynamically generated environment maps are impossible (because there is no scene information)' — the studio worked around this with baked shadowmaps + transform-matrix lookups rather than true real-time reflections/shadows. https://projectionspace.wordpress.com/2016/05/06/pillars-of-eternitys-rendering-techniques/
- Normal-mapped 2D lighting (Sprite Lamp / Laigter / SpriteIlluminator lineage): a normal map's RGB channels encode surface-facing direction (128,128,255 = flat facing camera), letting an engine fake volume against a moving light; Laigter is free/open-source, batch-CLI capable, and auto-generates normal+specular+parallax+AO maps from a flat painted sprite/region. https://laigter.readthedocs.io/en/latest/HowTo/normal-map-generation.html ; https://github.com/azagaya/laigter
- Unity's URP 2D Renderer ships a native normal-mapped-lit sprite shader ('Sprite-Lit-Default' + Light2D) but this system does NOT exist on the legacy Built-in Render Pipeline; built-in RP's old 'Sprites/Diffuse' shader has no Light2D/normal-map integration and isn't even portable to URP without the Render Pipeline Converter — a backdrop-quad N·L lighting shader must be hand-written in CG/ShaderLab for built-in RP. https://docs.unity3d.com/Packages/com.unity.render-pipelines.universal@14.0/manual/PrepShader.html ; https://blog.febucci.com/2018/07/sprite-diffuse-shader/
- Flipbook/sprite-sheet texture animation is the standard technique for fire, smoke, and embers overlays: a grid-of-frames texture is UV-indexed by time, and randomizing frame order (vs strict looping) breaks up repetition for a more believable flame; Unity's Shader Graph Flipbook Node is the modern node version, but Shader Graph only targets URP/HDRP, not built-in RP — built-in RP needs an equivalent hand-written CG shader (column/row/frame-count/fps properties driving UV offset). https://www.vfxapprentice.com/blog/what-are-flipbooks-in-games ; https://docs.unity3d.com/Packages/com.unity.shadergraph@6.9/manual/Flipbook-Node.html
- Vertex-animated foliage/cloth wind sway for 2D sprites: the Moonblog 'FoliageWaver' CG surface shader rotates mesh vertices about a pivot using texcoord.y and a time-driven wave function, with tunable Wave Dissipation/Friction/Bending/Speed — directly portable to built-in RP since it's plain CG, unlike the Shader-Graph wind-sway tutorials which target URP. http://blog.moondrop.no/2016/07/making-foliage-to-wave-in-a-2d-game-with-wind/
- Cinemagraph technique (Kevin Burg/Jamie Beck, ~2011): mask a small moving region (water, flame, hair, smoke) over an otherwise-frozen still, looped as either a 'repeat' loop (first/last frame must match exactly) or a 'bounce' loop (plays forward then reverse, more forgiving for subtle motion) — this masking model is the direct ancestor of how PoE/Disco Elysium composite animated regions onto static plates. https://en.wikipedia.org/wiki/Cinemagraph ; https://borisfx.com/blog/how-to-make-cinemagraphs-in-4-simple-ways/
- AI image-to-video for elemental loops (2026 landscape): ambient/cyclical content (water, fire, smoke, clouds, foliage) loops far more convincingly than complex action because the loop seam is imperceptible in slow cyclical motion; practical prompt levers are 'seamless pattern/repeating tile' phrasing and 'fixed camera, static shot, on a tripod' to kill unwanted pans. Runway's Motion Brush (paint up to 6 regions + per-region motion trajectories) and Kling's strong idle-ambient-motion handling (fire flicker, cloth drift) are the two most cited tools for this specific use case; LTX-2.3 leads for first/last-frame-conditioned seamless transitions (ComfyUI 'LTX 2.3 First Last Frame' workflow). https://morphic.com/ai-glossary/Looping ; https://github.com/Lightricks/LTX-Video
- AnimateDiff (via ComfyUI 'Animate Diff High Res Loops' + IP-Adapter) is the lightest-weight path to a seamless single-still loop (matches first/last frame, doubles length via reversed-frame append), but by 2026 industry commentary frames it as niche/nostalgic vs. production-grade LTX-2.3/Wan/CogVideoX for anything beyond quick throwaway loops. https://ltx.io/blog/best-open-source-video-generation-models
- EbSynth (and its newer browser-based EbSynth 2) is NOT generative AI — it's a texture-synthesis algorithm that propagates one hand-painted keyframe's style across an entire video's motion/texture; the practical fit here is OFFLINE authoring (paint one frame of a fire/water effect, propagate across a short filmed/rendered reference clip) to bake a flipbook texture cheaply, rather than a runtime technique. https://ebsynth.com/ ; https://80.lv/articles/photoshop-for-video-ebsynth-2-released
- loopFlow (After Effects plugin) is the most direct tool-match for 'compositing an AI-generated loop back onto the source plate region': you draw two masks defining a flow area+direction and it slides/blends two copies of the SAME image along a generated mesh between them for continuous flowing-water/smoke/fabric/flame motion without any frame-by-frame work or external video-gen call. https://aaeplugins.com/plugins/loopflow/ ; https://irrealix.com/plugin/loopflow
- Metal-specific gotchas for a built-in-RP backdrop-quad shader on macOS: Metal does not support geometry shaders at all (rules out any geometry-shader-based amplification trick); historical Unity forum reports show ShaderLab shaders working on Windows/DX but failing silently on Metal over compute-buffer binding-index mismatches, and URP changelogs list several macOS-Metal-specific MSAA and 2D-normal-map-quality bugs that were fixed only in later package versions — test the hand-rolled normal-map/flipbook shader on the actual Metal target early, don't assume DX-validated CG code ports 1:1. https://forum.unity.com/threads/shader-not-working-with-macos-metal.1358912/ ; https://docs.unity3d.com/2020.1/Documentation/Manual/Metal.html

**Actionable:**
- Layer a thin translucent 3D plane over the camera-locked backdrop quad for each elemental effect (water, fire, fog) with its OWN material/shader — do not try to animate the backdrop quad's base texture itself; this is the PoE/Disco Elysium pattern (paint stays static, effects are separate real-time layers).
- Write one hand-rolled CG/ShaderLab flow-map shader (two scrolling/distorting normal or flow textures, phase-blended per Catlike Coding's math) and reuse it for water AND fire/lava regions by swapping the base texture and tint — matches how Disco Elysium reused one water shader for ripples, fish, icebergs, and coastline.
- Run painted backdrop regions (water, stone, cloth) through Laigter (free, scriptable CLI) to auto-generate normal maps, then hand-write a simple N·L directional-light CG shader for the backdrop quad material, since built-in RP has no equivalent to URP's Sprite-Lit-Default/Light2D — this must be custom, budget the eng time.
- Add a hand-written flipbook/sprite-sheet CG shader (frame-count/fps/columns/rows properties driving UV offset, with randomized frame order to avoid a visible loop) for torch fire, embers, and dust-mote particle overlays composited over specific backdrop regions.
- Apply the Moonblog 'FoliageWaver'-style vertex-displacement wind shader (rotate vertices about a pivot via texcoord.y + time wave, plain CG so it's built-in-RP-portable) to any foreground painted cutout planes representing foliage, banners, or cloth for the cheapest possible 'alive' signal.
- Add a handful of small 2-6 frame sprite-sheet ambient-life actors (birds, insects) moving along simple paths across specific backdrop regions — this is literally what Disco Elysium's 'seagulls' and PoE2's ambient dressing do, and it is far cheaper than any AI video-loop pipeline for the same perceptual payoff.
- For any AI-generated elemental loop (Kling/Runway/LTX), prompt with explicit 'seamless pattern/repeating tile' + 'fixed camera, static shot, on a tripod' language, then bake the result down to a flipbook texture or a small masked video-texture region rather than trying to composite full-frame video onto the backdrop quad at runtime.
- Test the built-in-RP backdrop shader (normal-map lighting + flipbook UV) on the actual macOS Metal target early in a spike — do not assume a DX-validated CG shader behaves identically; Metal has documented compute-buffer binding and historical MSAA/2D-normal-map bugs that only show up on this backend.

**Dead ends:**
- Don't reach for Unity Shader Graph tutorials (Flipbook Node, wind-sway node graphs) as drop-in solutions — Shader Graph only targets URP/HDRP, not the built-in Render Pipeline; every node-graph tutorial found needs re-implementation in hand-written CG/ShaderLab.
- Don't port URP's Sprite-Lit-Default + Light2D normal-mapped lighting system as-is — it doesn't exist on built-in RP, and the official Unity migration path (Render Pipeline Converter) is one-way toward URP, not something you can borrow piecemeal.
- Don't chase geometry-shader-based amplification tricks (common in generic real-time-VFX tutorials) — Metal does not support geometry shaders at all, so any technique relying on them is a non-starter on macOS.
- Don't lean on AnimateDiff as the production AI-loop tool for 2026 — industry consensus now frames it as a niche/nostalgic option; LTX-2.3/Wan/CogVideoX are the current production-grade choices for first/last-frame-conditioned seamless loops.
- Don't try to replicate Pillars of Eternity's full Maya 4-pass (final/depth/normal/albedo) pre-bake pipeline — it explicitly sacrifices true dynamic shadows/reflections ('no scene information') and requires a heavy offline-3D-render tooling investment that's disproportionate to a single camera-locked backdrop quad.

### 3D-char-on-2D-art style cohesion
Researched 3D-character-on-2D-painted-art cohesion beyond the failed Kuwahara/posterize post-process approach. Consistent pattern across every genuinely shipped example (WoW, Dota2, Torchlight, Guilty Gear Xrd, Sable): style cohesion is won at the TEXTURE/MESH/VERTEX layer (painted-in lighting on the albedo, hand-edited vertex normals, flat authored shading), not by a screen-space camera filter. Basic Kuwahara is documented to inherently cluster/smear and scale ~quadratically with radius (one UE5 report: 100x slowdown); this matches the observed 3.2/10 panel failure and suggests the filter-layer approach itself, not just tuning, is the wrong lever. Toon ramp+matcap hybrids and AI img2img texture re-bakes (Scenario/StableGen/Stable Projectorz) both bake stylization into shader/texture space, which is inherently animation-safe (zero smear) and cheap or free at runtime. The 'render-3D-to-sprite' lane (Dead Cells, modernized with AI reference-pinned img2img) has a real shipped precedent but trades away free camera/dynamic lighting and introduces its own consistency-drift problem unless rigorously reference-pinned.

**Findings:**
- WoW/Dota2/Torchlight 'hand-painted stylized' look bakes ALL lighting+shadow into the diffuse map (AO/bent-normal green channel as light base, then hand-painted over it), not a runtime shader; no PBR commitment. https://80.lv/articles/002mrs-crafting-a-wow-diorama-textures-painting-lighting
- Valve's Dota2 workshop guide: hero readability fixes shown are texture-level -- add secondary skin-translucency color, remove painted-in shadows under cloth -- not shader/lighting tricks. https://media.steampowered.com/apps/dota2/workshop/Dota2CharacterTextureGuide.pdf
- Procedural 'hand-painted edge-wear' trick: Pointiness(Geometry) -> ColorRamp (~0.45-0.55) baked into diffuse; cheap, offline, animation-irrelevant since it lives in texture-space not per-frame. https://polycount.com/discussion/204524/guide-on-how-to-create-dota-2-assets-with-blender
- Ramp+matcap toon hybrids (MK Toon, Toon RP, ORL Toon): 1D lighting ramp for diffuse banding + matcap for highlights/reflections, entirely in vertex/fragment shader -> zero smear risk, trivially survives skeletal animation, no extra render passes. https://github.com/Delt06/urp-toon-shader
- Anisotropic Kuwahara (Kyprianidis/Kang, GPU Pro 2010) fixes basic Kuwahara's clustering via a structure-tensor pass, but cost still scales ~quadratically with radius; UE5 forum documents a naive nested-loop port causing a 100x slowdown. https://forums.unrealengine.com/t/ue5-1-postprocess-custom-shader-100x-slowdown-kuwahara-filter/693332
- Basic (non-anisotropic) Kuwahara is documented to produce 'clustering artifacts' inherently, not just from bad tuning -- matches the WorldOS panel-failed run (3.2/10); needs the anisotropic/structure-tensor upgrade to avoid this. https://www.umsl.edu/~kangh/Papers/kang_cgf09.pdf
- Unreal stylized-rendering case study explicitly rejected raw screen-space Kuwahara/blur filters as reading like 'an image slapped over the camera'; instead projected a world-space normal map so UV distortion stays anchored to geometry and stable under motion. https://www.therookies.co/entries/7431
- Assemble With Care ships diffuse<->brush-stroke lerp + simplex vertex wobble, both STEPPED at 5fps (not continuous) specifically to avoid perceptible smear -- but only ever applied to static inanimate props, not skinned characters (unverified for rigs). https://medium.com/@ustwogames/technical-art-in-assemble-with-care-9b31792add10
- Guilty Gear Xrd (GDC 2015): 3D-reads-as-2D via an authored pipeline, not a shader gimmick -- hand-edited vertex normals (no normal maps), ~40k tris, rule 'kill everything that looks 3D.' Survives full skeletal fighting-game animation since it's baked into rig/mesh. https://www.ggxrd.com/Motomura_Junya_GuiltyGearXrd.pdf
- Sable (GDC 2022): flat Moebius shading (thin outline, no gradient) solves depth/readability loss by layering light+shadow+fog on top, not more filtering. Lower painterly-realism ceiling but robust and animation-free since it IS the base shading model. https://gdcvault.com/play/1027721/The-Art-of-Sable-Imperfection
- Scenario/StableGen/Stable Projectorz: img2img texture re-bake (depth+normal ControlNet + style-reference image) re-paints an existing 3D asset's albedo ONCE offline; runtime cost is zero, survives skeletal animation trivially like any hand-painted texture. https://help.scenario.com/en/articles/reskinning-assets/
- Dead Cells (2018): posed the 3D model in a custom low-res, no-smoothing renderer (~50px char height) to fake pixel art; keyframe+interpolation animation. Biggest win was asset/animation REUSE across enemies, not lighting fidelity -- ceiling capped by target resolution. https://www.gamedeveloper.com/production/art-design-deep-dive-using-a-3d-pipeline-for-2d-animation-in-i-dead-cells-i-
- Modernized AI sprite pipelines (PixelLab, Layer.ai, Gamelabs' shipped 'Age of Steam Tower Defence'): pin every directional/pose generation to ONE canonical reference portrait (denoise 0.35-0.65 by subtlety); unpinned generation is the #1 documented drift failure mode. https://gamelabstudio.co/
- Sprite Sheet Diffusion (arXiv 2412.03685) adapts AnimateAnyone (ReferenceNet+PoseGuider+Motion Module, SD-v1.5) to keep sprites consistent across an action's frames; OpenPose/DWPose don't generalize to stylized art, so pose-conditioning itself needs a style-aware model. https://arxiv.org/html/2412.03685v1
- Velocity Skinning (Rohmer et al., Eurographics 2021): real-time GPU extension on standard LBS/DQS deriving squash/floppy secondary motion from joint velocity, no physics sim, works on ANY skinned mesh -- an orthogonal fix for GGX's 'reads as CG because too perfect' problem. https://arxiv.org/abs/2104.04934

**Actionable:**
- Move stylization off the post-process/screen-space layer onto texture+mesh: bake painted lighting/shadow cues into character albedo (WoW/Dota2 technique) instead of deriving them from a camera-space Kuwahara/posterize filter -- likely why the tried approach scored below baseline.
- Adopt a ramp+matcap toon hybrid (Toon RP / MK Toon / ORL Toon patterns) as the base character lighting model: cheap, fully vertex/fragment-shader based, zero smear risk, animation-safe by construction.
- Pilot AI texture re-bake (Scenario img2img-texture, or StableGen/Stable Projectorz ControlNet-depth+style-reference in Blender) to push existing character albedo maps toward the PoE2 reference palette/brushwork offline, once, at zero runtime cost.
- If retrying any screen-space painterly filter, replace raw Kuwahara with the world-space-normal-projected UV-distortion pattern (Rookies/Unreal case study) -- explicitly designed to stay stable under camera/character motion, unlike naive Kuwahara's clustering/100x-slowdown failure modes.
- Study Guilty Gear Xrd's GDC talk (hand-edited vertex normals, no normal maps, 'kill everything that looks 3D') as the qualitative bar for how much manual/authored pass real cohesion requires -- it was never a shader trick.
- Keep Sable's flat-shade + line-art (Moebius) approach as a fallback lower-ceiling-but-robust style if painterly-realism cohesion keeps failing; its GDC talk gives the specific fix (layer in light/shadow/fog) for the depth-readability cost of flat shading.
- If evaluating a render-to-sprite lane, mandate reference-image-pinning (one canonical portrait feeding every directional/pose generation) -- the documented fix for AI sprite identity drift; never generate views independently.
- Evaluate Velocity Skinning (real-time, GPU, works on any existing skinned mesh/rig) as an orthogonal, cheap addition for stylized secondary motion -- addresses the 'too-perfect, reads as CG' root cause GGX names, independent of whichever shading approach is chosen.

**Dead ends:**
- Naive nested-loop Kuwahara/posterize post-process filters: quadratic cost blowup with radius (one UE5 report measured a 100x slowdown) plus inherent clustering artifacts even when tuned -- matches the observed 3.2/10 failure; don't keep tuning this filter, change layers instead.
- Screen-space painterly distortion applied uniformly to the camera without world-space-normal stabilization: explicitly documented to read as 'a filter slapped over the camera' rather than integrated stylization, and gets worse (not better) under camera/character motion.
- Generating multi-view/multi-pose AI sprites independently per frame without reference-pinning: causes severe identity drift (proportions, palette, face) -- documented as the #1 production failure mode in both Scenario's and Layer.ai's case studies.
- Full 'render-3D-to-AI-sprite' as the primary lane for a renderer that wants free camera + dynamic real-time lighting: the Dead Cells/PixelLab precedent trades those away for pre-baked directional sprites, so it conflicts with that specific requirement unless used only as a prebaked fallback tier.
- Extending Assemble With Care's stepped brush-stroke/vertex-wobble trick to skinned characters without new validation: the shipped implementation was only ever verified on static inanimate props, not rigged/animated characters, so its smear-avoidance claim doesn't transfer for free.
